## 一、保密红线

以下内容属于内部信息，不进入任何公开文章、公开页面、公开评论：

1. 完整技术架构、内部模块依赖关系、部署链路细节。
2. 鉴权机制、OAuth 回调逻辑、密钥存放位置、后端 Worker 接口设计。
3. 仓库结构、CI/CD 完整工作流、分支管理策略。
4. 个人身份关联敏感信息、R2 存储规则、存储桶权限策略。
5. 任何真实 Token、密钥、Cookie、账号标识。

公开场合只允许描述“访客能感知的功能变化”，不描述“功能如何实现”。

## 二、当前架构完整梳理

### 技术栈

- Astro 7 静态站点生成。
- Svelte 5、TypeScript、Tailwind CSS。
- 内容体系：`posts`（文章）、`dynamic`（动态）、`spec`（关于/友链/留言）。
- 站点配置集中在 `src/config/*.ts`，包括导航、网站导航、相册、图床、友链、打赏、音乐、背景壁纸等。

### 部署链路

- 源码托管在 GitHub 仓库。
- GitHub Actions 负责安装依赖、构建、部署。
- Cloudflare 侧存在两个 Worker 角色：博客站点 Worker 负责对外页面与静态资源；R2 代理 Worker 负责 `static` 域名的图片、视频、音乐代理等资源访问。
- 主域名与 `www`、`static` 已接入 Cloudflare 路由。
- 评论使用 Giscus，与仓库 Discussions 关联。

### 现有页面

- 主页：全屏壁纸、首页区块、文章流。
- 文章：归档、分类、标签、搜索。
- 网站导航：书签导航 + 图床入口。
- 动态：本地动态文件 + 动态 API。
- 记录：动态、归档、分类、标签、相册、留言板入口。
- 关于、友链、留言板、打赏、相册、图床、高级图床。

## 三、后续开发规划

### 目标形态

不采用“本地完整源码 + 本地运行预览”的编辑方式，目标是在浏览器内完成大部分内容与结构维护，并且访客前台保持纯只读。

### 规划模块

1. 独立管理入口
   - 计划使用独立子域名承载管理端，与主站完全隔离。
   - 主站不加载任何管理代码，访客页面保持纯静态。
2. 在线内容管理
   - 文章、动态、记录、关于、友链、留言等 Markdown 内容在线编辑。
   - 编辑器必须匹配当前内容 schema，避免 frontmatter 字段错误。
3. 配置数据化
   - 将导航、网站导航、相册、图床、友链、打赏等 TS 配置迁移为 JSON。
   - TS 层只做读取和类型约束，编辑端只写结构化数据，避免手写 TS 导致构建失败。
4. 站点结构树
   - 左侧 XMind 风格结构树，拖拽调整模块顺序、增删栏目、修改名称。
   - 结构树操作最终落为 JSON 配置变更。
5. 图床上传
   - 对接 R2 上传能力，上传后自动生成图床配置与直链。
   - 上传接口必须鉴权，禁止匿名写入。
6. 一键发布
   - 保存后自动校验配置、提交 Git、触发自动构建部署。

## 四、安全推演与风险清单

### 1. 信息泄露风险

- 前端源码嗅探：压缩后的 JS/CSS 仍可能暴露内部接口路径，需避免在公开产物中出现敏感端点。
- 接口抓包：所有管理接口必须鉴权、限流、校验来源。
- 打包产物溯源：避免把仓库路径、内部文件名、构建命令写入可被公开访问的注释或错误提示。
- 公开文章反向推导：公开文章只描述功能，不描述架构。
- 密码文章源码泄露：网站前端加密不等于仓库源文件加密，仓库可见性必须单独控制。

### 2. 网络攻击风险

- 域名攻击：为管理子域名配置独立安全策略，避免与主站共享不必要的权限。
- Worker API 滥用：未授权请求必须返回拒绝，不能成为代理跳板。
- 未授权后台访问：管理入口需要多重鉴权，不能只依赖“路径保密”。
- 越权读写：管理端只能操作白名单内的文件与路径，禁止路径穿越。
- 配置写入导致构建雪崩：写操作前做 schema 校验与字段白名单校验。

### 3. 爬虫与批量抓取

- 区分普通搜索引擎与恶意批量抓取，按需配置 robots、访问频率限制、特征识别。
- 重要资源不要提供无限制的批量下载入口。
- 避免把整站资源清单、内部文件树暴露在公开页面。

### 4. CMS / 管理端专属风险

- OAuth 鉴权绕过：回调地址必须校验，授权范围最小化，账号白名单严格控制。
- 非法提交文件：只允许编辑已声明类型与路径的文件。
- 构建雪崩：提交前校验，构建失败时保留线上上一版本。
- Token 泄露：所有密钥只存在服务端环境变量，绝不放前端。

## 五、公开文章写作边界

### 可以写

- 网站接下来会增加哪些“访客能感受到”的能力。
- 内容会更方便发布、站点结构会更灵活、素材管理会更顺手。
- 对访客阅读体验的优化方向。

### 不能写

- 管理后台域名、鉴权方式、OAuth 流程。
- Worker 接口路径、R2 存储策略、存储桶名称。
- GitHub Actions 流程、分支策略、部署命令。
- 配置文件迁移细节、CMS 选型、内部依赖。
- 任何真实密钥、账号、Token、Cookie。

## 六、开发约束

1. 信息安全与架构保密优先级高于功能完整度。
2. 不复制第三方项目作为模板，只参考其共性缺陷并规避。
3. 管理端与前台彻底隔离，前台不加载管理代码。
4. 所有配置迁移必须保留现有功能兼容性。
5. 每次上线前完成构建验证，失败不覆盖线上版本。

## 七、目标架构设计（内部）

### 整体分层

1. 前台层
   - 现有 Astro 静态站点，纯只读。
   - 不加载任何管理代码，不包含管理接口路径。
2. 管理端
   - 独立子域名承载，与主站隔离。
   - 包含内容编辑器、结构树编辑器、配置表单、图床管理、发布入口。
3. 网关层
   - Cloudflare Worker 承担：OAuth 登录、GitHub API 代理、文件读写、路径白名单、schema 校验、R2 上传、发布触发。
   - 所有密钥只存在 Worker 环境变量或 Secrets。
4. 数据层
   - GitHub 仓库保存 Markdown 内容与 JSON 配置。
   - R2 保存图片、视频等静态素材。
5. 发布层
   - GitHub Actions 完成构建与部署。
   - 构建失败时不覆盖线上版本，保留上一版本可回滚。

### 管理端与前台隔离

- 主站与后台使用不同域名，避免后台资源被前台引用。
- 主站静态产物中不出现后台路径、接口地址、密钥名。
- 管理端预览通过 iframe 加载主站，模拟“在网站里编辑网站”的体验，但编辑逻辑完全在后台。

### 配置 JSON 迁移

- 目标迁移：导航、网站导航、相册、图床、友链、打赏等配置。
- 迁移原则：TS 文件保留为入口，只负责读取 JSON 和提供类型约束；编辑器只写 JSON。
- JSON 必须带 schema，保存前校验字段类型、必填项、引用关系。

### 结构树编辑器

- 数据模型采用树形结构，节点对应页面、栏目、模块。
- 操作能力：拖动排序、增删节点、改名、启用/停用、修改图标和链接。
- 落盘时生成对应 JSON，并同步校验导航顺序约束。

### R2 图床

- 管理端上传后由网关写入 R2，返回可公开访问的直链。
- 上传必须鉴权，限制文件类型与大小。
- 图床记录同步写入配置 JSON，前台图床页面只读展示。

### 发布流程

- 编辑保存 → 网关校验 → 提交 Git → 推送触发 Actions → 构建部署。
- 关键节点增加校验：frontmatter 校验、JSON schema 校验、构建前语法检查。

## 八、开发过程中可能遇到的问题

1. 公开仓库导致敏感信息泄露
   - 风险：密码文章源文件、内部文档、历史提交中的密钥都可能被仓库读者看到。
   - 对策：仓库私有化或敏感文件移出仓库；清理历史提交；Token 一律轮换。
2. 内容 schema 不匹配
   - 风险：CMS 写出的 frontmatter 与 Astro schema 不一致，构建直接失败。
   - 对策：编辑表单由 schema 驱动，保存前先校验。
3. TS 配置迁移兼容
   - 风险：现有代码直接引用 TS 常量，迁移 JSON 后导出形态变化。
   - 对策：保持 TS 入口，JSON 只作数据源，逐步迁移并保留兼容层。
4. OAuth 与回调安全
   - 风险：回调地址伪造、state 校验缺失、授权 scope 过大。
   - 对策：固定回调地址、校验 state、最小权限 scope、账号白名单。
5. Worker API 滥用
   - 风险：未授权访问、路径穿越、批量请求打满配额。
   - 对策：鉴权中间件、路径白名单、限流、审计日志。
6. 构建雪崩
   - 风险：错误配置或错误 frontmatter 触发构建失败，甚至影响线上。
   - 对策：提交前校验、CI 失败保留旧版本、支持人工回滚。
7. R2 上传安全
   - 风险：匿名上传、超大文件、恶意文件类型。
   - 对策：鉴权、大小限制、类型白名单、资源前缀隔离。
8. 结构树复杂度
   - 风险：拖拽造成循环引用、层级混乱、与现有导航规则冲突。
   - 对策：先定数据模型和约束，再做拖拽交互，保存前校验。
9. 多设备与并发
   - 风险：浏览器缓存不一致、两个设备同时编辑导致覆盖。
   - 对策：Git 提交原子化，冲突时提示，先做单用户编辑。
10. 爬虫与源码扒取
    - 风险：静态产物被批量抓取，接口被枚举，源码映射被还原。
    - 对策：压缩混淆、不暴露接口、robots、限流、重要资源鉴权。
11. 域名攻击
    - 风险：DNS 劫持、子域接管、SSL 配置错误。
    - 对策：全站 HTTPS、CAA、子域验证、Cloudflare 托管。
12. 评论与 slug 稳定
    - 风险：文章 slug 变化导致 Giscus 讨论丢失。
    - 对策：slug 保持稳定，迁移时保留旧 slug 或跳转。
13. 性能与构建时间
    - 风险：大图、大量文章、管理端预览 iframe 拖慢体验。
    - 对策：懒加载、缓存、按需构建。
14. 备份与回滚
    - 风险：误删、误改、发布异常。
    - 对策：Git 历史、定期备份、部署版本保留、快速回滚方案。

## 九、需要做到的程度与验收标准

1. 保密程度
   - 公开产物中不出现管理端路径、密钥名、内部文件名。
   - 公开文章只描述功能，不描述实现。
   - 仓库可见性与敏感文件存放方式必须明确控制。
2. 权限程度
   - 未授权访问一律拒绝，不返回敏感信息。
   - 只有白名单账号可编辑提交。
   - 写操作只允许白名单路径，禁止路径穿越。
3. 可用性程度
   - 前台不受管理端故障影响。
   - 管理端故障不阻塞前台访问。
4. 数据安全程度
   - 所有写操作先校验后提交。
   - 错误配置不得导致线上不可恢复。
   - 构建失败保留上一版本，可回滚。
5. 体验程度
   - 管理端浏览器跨设备可用。
   - 编辑保存到上线流程尽量精简。
   - 普通访客始终无需登录即可浏览。
6. 可维护程度
   - 配置 JSON 有 schema。
   - 结构树与配置双向一致。
   - 内部文档与实现同步更新。
7. 测试程度
   - 每次发布前至少通过构建。
   - 鉴权、校验、回滚等关键路径有测试覆盖。

## 十、开发顺序与里程碑

- M1：管理端子域、网关骨架、OAuth 白名单、文章与动态在线编辑。
- M2：配置 JSON 迁移、表单化编辑、网站导航与图床配置可维护。
- M3：结构树编辑器、R2 图床上传、一键发布流程。
- M4：安全加固：防爬、限流、审计、备份、回滚、密钥轮换。
